# 02 · User stories and acceptance

**Objective:** Define observable success and recovery before UI design. The requirements below are product acceptance scenarios, not new test results. Use synthetic accounts, offers and contracts during demonstration.

| ID / story                                                                         | Given → When → Then                                                                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AUTH · As a visitor, I want recognizable sign-in and recoverable access.           | Given no session, when I choose a public sample, then no OTP is needed. Given an email was entered, when OTP send/verification or session restoration fails, then I see a next step and the email is preserved. Once accepted, the same OTP is not resubmitted.            |
| FIRST · As a new user, I want to choose whether to fill my profile.                | Given an empty account, when I open Home, then Explore and Fin are reachable and a single optional profile invitation explains the benefit.                                                                                                                                |
| PROFILE · As a borrower, I want to correct my inputs.                              | Given I add or edit stated monthly amounts in Profile, when saved successfully, then recalculations reflect my saved values; validation or connection failure preserves valid input.                                                                                       |
| CAP · As a borrower, I want to distinguish room to borrow from cash remaining.     | Given a valid profile, when I view Home, then the two measures are labeled with the relevant time unit and not presented as a credit limit or a borrowing recommendation.                                                                                                  |
| ASK · As a caller to Fin, I want to verify why a number appeared.                  | Given an incomplete question, when I ask what a loan costs, then the local flow asks for missing essential terms rather than inventing them. Once provided, values are traceable; external interpretation and persistence require their respective existing confirmations. |
| FIND · As a new borrower, I want to understand an offer's advertised terms.        | Given search results, when I open details, then I see source/status and rate basis; missing data is not a guaranteed quote. When no filters match, I can clear filters.                                                                                                    |
| COMP · As a shopper, I want an honest A/B.                                         | Given two plans, when I compare the same amount and term, then both show comparable amounts and fee uncertainty; missing fees prevent total-cost ranking. Unsupported overlap has a path to adjust.                                                                        |
| SIM · As a borrower, I want to model terms quoted to me.                           | Given a catalog entry or direct calculator, when I choose personal terms, then advertised terms do not silently populate personal assumptions. Then a valid preview exposes first payment, known total and schedule; invalid inputs stay editable.                         |
| DOC · As a contract holder, I want to confirm extracted numbers.                   | Given a synthetic document in review, when extraction is uncertain/unavailable, then manual correction is available; only explicit save uses reviewed values. Given another user, they cannot see the file or analysis.                                                    |
| SAVE · As a planner, I want to save without creating debt.                         | Given a preview with explicit assumptions, when I confirm Save, then one snapshot appears and the ledger remains unchanged; cancel creates nothing.                                                                                                                        |
| TRACK · As a borrower who has signed, I want a new tracked loan.                   | Given a saved estimate and a real first due date, when I explicitly confirm starting a tracked loan, then the obligation appears; the distinction is visible.                                                                                                              |
| REPAY · As a returning borrower, I want to record a payment without sending money. | Given a tracked plan, when I explicitly confirm a period as paid, then the owned ledger persists the new status across reload and never represents a bank transaction.                                                                                                     |
| SETTINGS · As a user, I want controls I can find and reverse where appropriate.    | Given I change appearance or language, when I reopen the app, then my choices persist. Given I delete one history after confirmation, then the other history and profile remain.                                                                                           |

## Journey outcomes and recoveries

| Journey                    | Success                                                                                                                                   | Recovery                                                                                                                                                                   |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A · First-time exploration | Observe a public example → optionally sign in → see product detail and source → identify assumption and cost, with an optional estimator. | Keep existing email through retry; if no product matches or terms are unavailable, clear filters or use the manual simulator.                                              |
| B · AI assistance          | Ask in Vietnamese → confirm assumptions → view grounded explanation or stress test → optional explicit save.                              | Ask for missing inputs; local tools remain available if external consent is declined or provider fails; resume without saving automatically.                               |
| C · A/B comparison         | Align amount and term → compare cost timing and exclusions → continue with own terms.                                                     | Adjust assumptions; if fees unknown, refrain from ranking by total cost and go back without losing the user's selection.                                                   |
| D · Contract review        | Upload synthetic file → inspect evidence → manually correct doubtful fields → preview and optional explicit save.                         | Invalid file can be replaced, unreadable field can be entered manually, and cancel/delete stays scoped to owned item.                                                      |
| E · Returning repayments   | Home next payment or Loans → identify tracked status → mark one period explicitly → verify reload.                                        | If no tracked contract, explain the difference and browse estimates; if a marking request fails, show recovery and reload verified state, not optimistic final settlement. |

**Gate:** All five journeys have an observable outcome, a recovery flow and state boundaries. Coverage of these stories by the new UI must be recorded in Stage 7; riskier statements are gates, not completed owner validation.
